# 斗地主规则与结算契约

斗地主是三人在线策略回合制游戏，包含一名地主和两名农民。房间满三席后开始，席位可由真人或受控 AI 占用。

## 房间配置与固定规则

用户可配置项只有：

| Key | 含义 |
| --- | --- |
| `enableLaizi` | 发牌前从 3 至 2 的 13 种普通点数中等概率确定癞子，并启用癞子牌型识别与癞子炸弹。 |
| `allowSingleAttachment` | 控制三带一和飞机带单是否允许单牌附件。 |

固定规则为一副 54 张牌、每人 17 张、3 张底牌。房间基础分 `R` 取本局固定规则 `ruleConfig.baseScore`，当前种子为 `1`，不是创建房间时的用户可选项。新局按 `1 / 2 / 3` 叫分确定地主，本局底分 `B = R × 最终叫分`。明牌、加倍、春天/反春天、炸弹和王炸使用本局固定规则中的系数。

叫分核心采用[JJ 公开普通斗地主规则](https://www.jj.cn/special/baidu/webgame.html)：每人最多响应一次，后手只能叫更高的分，叫到 `3` 立即确定地主；否则一轮结束后由最高叫分者当地主，全部不叫则重新发牌。房间基础分与叫分合成本局底分的定义参照[波克公开计分规则](https://www.pook.com/games/ddz.html)。本项目保留全员明牌、个人加倍及可选癞子玩法作为扩展，不将这些扩展表述为上述普通叫分规则的组成部分。

## 阶段与动作

癞子玩法先确定并公开癞子点数，再洗牌发牌；普通玩法直接发牌。新局发牌后依次进入明牌、叫分、地主确认、加倍、出牌、结算和结束。明牌阶段仍由每名玩家依次选择明牌或不明，地主确认发放底牌后再由每名玩家依次选择加倍或不加倍。叫分完成不再进入抢地主。癞子展示、发牌、地主确认与结算展示通过 `RoomAutoAdvanceTask` 推进；它们不模拟玩家操作。

癞子点数与手牌、底牌的随机分配相互独立，不从底牌选取，也不排除底牌恰好含同点数牌。大小王不能成为癞子。癞子展示阶段手牌与底牌尚未生成，公开状态已有 `laiziRankCode`、`laiziRankValue` 和该点数四种花色的 `laiziCardCodes`；进入发牌阶段后，同点数的四张牌统一标记 `isLaizi`。三人均不叫地主时，重新确定癞子后再发牌。

`PLAY_CARDS` 是 `COMPOSED` 动作：客户端提交 `cardInstanceIds`，服务端识别牌型、校验手牌归属和压制关系，再归一化为 `ResolvedGameAction`。以下动作是 `ENUMERATED`：

```text
SHOW_CARDS, SKIP_SHOW_CARDS,
CALL_LANDLORD, PASS_CALL,
DOUBLE, PASS_DOUBLE,
PASS
```

`CALL_LANDLORD` 的枚举选项携带 `payload.bidScore`，根据当前最高叫分只生成仍合法的更高分值；`PASS_CALL` 表示本次不叫。客户端提交选项 `actionId`，服务端按当前版本再次解析，不能通过自填分值绕过合法候选。旧版本在途局仍可使用 `ROB_LANDLORD / PASS_ROB`，新局不提供这两个动作。

起叫座位沿用本项目的可恢复顺序：首轮由已落盘洗牌结果生成私有种子，重新发牌沿用该种子并按发牌轮次轮换，连续三轮各座位恰好起叫一次。该实现不新增随机调用，也不添加连续不叫后强指定地主的兜底规则；重发轮次的具体轮换方式是项目实现约定，不冒充参考来源未明确的细则。

提示和自动候选只提供候选或推荐。`POST /rooms/{roomId}/actions` 在每次提交时重新进行权威解析和合法性校验。

牌型识别以物理牌集合为输入，提交顺序与花色不改变牌型大小。多解时保留固定牌型家族优先级：王炸、天然炸弹、癞子炸弹、四带二对、四带二单、飞机带对、飞机带单、飞机、连对、顺子、三带一对、三带一、三张、对子、单张。同一牌型家族存在多种癞子分配时，选择主牌点数最高的合法解释；跟牌时按上述家族顺序选择能够压过目标的解释，不能因先遇到不可压的解释而拒绝整组牌。单张癞子仍按牌面点数，纯癞子炸弹仍按癞子点数；是否允许带单与王牌附件规则照常校验。手动出牌、Preview、提示和自动候选共用此识别入口。

## 自动决策、托管与恢复

AI、在线托管、离线 shell 和回合超时都进入同一条 `AUTOMATED_DECISION` 链路。平台根据当前回合成员创建 `ManagedTurnTask`，斗地主模块为全部可用 actionType 提供候选；候选在同一集合中评分和选择，必要时由斗地主私有 FallbackPolicy 从已验证候选中选择。选中的 `ActionSubmission` 会再次经过交互网关 Resolve，再进入 Runtime 和 Lifecycle。

自动候选与用户提示彼此独立。`PLAY_CARDS` 的自动候选使用斗地主内部搜索预算；提示使用独立的稳定顺序和 cursor。提示接口只返回 `selection`、`summary` 和 `nextCursor`，不公开候选评分、归一化动作或内部 actionId。前端使用提示 selection 填充手牌选择，再通过 Preview 和正式提交确认。

在线托管仅代表真人席位仍在线且由系统代打；shell 仅在 Presence 确认离线后形成。shell 玩家可通过 rejoin 恢复席位和手动操作。托管任务在房间锁内重新读取快照、当前行动者和成员控制状态，已取消托管、已恢复席位或已变化的回合不会执行排队任务。

## 理论结算

新规则中，底分 `B = 房间基础分 R × 最终叫分`，公共倍率 `G` 初始为 `1`。玩家个人行为系数 `P` 由明牌与加倍组成，当前两者各为 `×2`，同时选择则为 `×4`。地主与农民 `i` 的结算额为：

```text
pairAmount[i] = B × G × P[landlord] × P[farmer_i]
```

地主阵营获胜时，每名农民 `scoreDelta = -pairAmount[i]`，地主获得两份结算额的合计；农民阵营获胜时符号相反。两名农民的个人行为不同，结算额可以不同；所有玩家理论 `scoreDelta` 之和始终为零。

公共与个人因素按其作用范围分别计算，叫分只进入底分，不再重复进入倍率：

| 来源 | 产生时机 | 范围 | 当前种子系数 |
| --- | --- | --- | --- |
| 明牌 | 每名玩家在明牌阶段选择明牌时，各计一次。 | 该玩家个人因素 | ×2 |
| 叫分 | 地主确认后采用最高合法叫分。 | 本局底分 | ×1 / ×2 / ×3 |
| 加倍 | 每名玩家在加倍阶段选择加倍时，各计一次。 | 该玩家个人因素 | ×2 |
| 炸弹 | 每次实际打出炸弹，包括癞子炸弹。 | 公共倍率 | ×2 |
| 王炸 | 每次实际打出王炸；同次出牌不再叠加炸弹倍率。 | 公共倍率 | ×2 |
| 春天 / 反春天 | 出完牌进入结算时，按条件判定且至多命中一种。 | 公共倍率 | ×2 |

例如基础分 `R = 10`、最终叫 `3` 分，则底分 `B = 30`。打出一个炸弹而未触发其他公共因素时 `G = 2`；地主仅加倍、农民甲仅明牌、农民乙未明牌也未加倍，则两份结算额分别为 `30 × 2 × 2 × 2 = 240` 和 `30 × 2 × 2 × 1 = 120`。地主获胜时理论结果为 `+360 / -240 / -120`。全部不叫而重新发牌时，本轮叫分、倍率、明细和玩家阶段行为一同重置。

`globalMultiplier` 是公共倍率的唯一事实；`bidScore` 保存本轮最高叫分，确认地主后用于派生底分，不另存可漂移的底分副本。个人因素从本局规则和已提交的 `showCards / isDoubled` 行为派生。`multiplierDetails` 明确区分 `scope: GLOBAL` 与 `scope: PLAYER`；只有公共来源记录 `globalMultiplierAfter`，个人来源不伪装成公共倍率变化。倍率更新与动作同一次原子提交；重复请求由房间命令的 `requestId` 幂等和版本校验处理，不重放倍率事件。

底牌下只显示“底分”和“倍率”。定地主前底分尚未确定，显示 `—`；确认后显示 `B`。这里的倍率显示公共 `G`，玩家信息只显示“明牌”“加倍”标签，不显示个人倍率数字。结算使用上述成对公式，因此个人行为不同会使两名农民的积分不同。

`rulesVersion` 是唯一规则版本字段：`1` 为旧叫抢与全桌计分，`2` 为新叫分与成对计分；新局只创建版本 `2`，未知版本明确拒绝，历史缺字段的快照只映射为版本 `1`。旧在途局按原叫抢流程和全桌公式自然结束，不在部署时强行转换为新玩法。更早的旧个人倍率结构继续由旧版解析路径校验明细并归一化为旧全桌倍率；新版永不进入该归一化路径。计算器统一使用成对公式，旧规则传入的个人因素为 `1`，避免已计入旧全桌倍率的行为再次累乘。已经生成的历史结算及待平台入账的 `PENDING` 结算保留原理论结果，不追溯重算。

## 平台钱包结算

规则层只生成理论零和结算，不写入钱包。平台结算层根据余额生成实际结果：

- 真人失败方最多扣至零，不产生负余额。
- 获胜方获得完整理论正向分数。
- AI 的 `actualDelta` 始终为 `0`，不生成真人钱包流水。
- `systemDelta > 0` 表示平台净支出，`systemDelta < 0` 表示平台净收入。
- 真人对 AI 的结算仍按真人余额规则扣加分，并以 `systemDelta` 表达平台对手方差额。

## 终局收敛

Lifecycle 产生终局指令和理论结算；Post-turn Outbox 依次驱动平台结算、终局 GameView 推送、Finalize 与派生索引清理。恢复流程从权威房间和 RuntimeSnapshot 重建缺失任务，结算不会重放玩家动作。
